# Three-Repository CI Assessment

Status: synthetic pilot design, not execution evidence or architecture authority

## 1. Decision Summary

The public repository uses three synthetic archetypes to organize future pilot
qualification. They are not renamed private clients, real installations or
claims that synthetic runs have happened. Former private source revisions,
workflow links, run IDs, measurements and operational receipts are not exported.

```text
SafePilot(repository) :=
  FreshDependencyEvidence
  and RepresentableExecution
  and SameRunObservation
  and FailClosedFallback
  and ProviderAuthority
```

Every predicate must bind an independently admitted target and current source.
Missing or conflicting evidence remains unknown and cannot authorize omission.
Local analysis and non-enforcing shadow planning do not prove provider readiness.

The proposed order introduces one execution concern at a time:

1. A reporting-service archetype for coarse lane selection and credential isolation.
2. An application archetype for governed witness selection and mixed execution profiles.
3. An extension-service archetype for capacity-bound adaptive sharding.

This is a bounded sequencing proposal, not a measured cost or repository-quality
ranking. Reopen it when the actual consenting target has different constraints.

### 2.1 Synthetic FullCI Fallback Scenario

Construct an isolated target with missing coordinator endpoint or installation
configuration. The requester must return the admitted typed failure, and the
consumer must execute the complete native FullCI route through its unchanged
stable gate. Bind every assertion to the exact generated source and event.

This is a required experiment, not a report that it passed. A reachable plan
endpoint, target trust root, repository registration and selected-plan canary
need separate evidence. Compare repeated, controlled baseline/treatment runs;
do not infer causal coordination overhead from one wall-time difference.

## 3. Repository Findings

The following are design questions for synthetic archetypes, not factual
findings about external repositories.

### 3.1 Application Archetype

Model backend, frontend, end-to-end and optional agent lanes with independent
obligations. A product-owned test-capability map can supply witness intent;
filenames and raw inventory counts cannot prove test adequacy.

Required constraints:

- Keep GitHub-hosted and self-hosted work in distinct execution profiles.
- Do not flatten heterogeneous workloads into one untyped shard pool.
- Admit every bounded manifest against current item and byte limits.
- Prefer governed work-unit granularity to raising limits without a resource argument.
- Prove that selected witness identities are current, unique and complete.

### 3.2 Extension-Service Archetype

Model integration-specific prerequisites, runner groups and labels before
choosing shard count. If changes cross component boundaries, coarse omission
may offer little benefit; that is a hypothesis to measure, not an assumption.

Duration-informed partitioning is admissible only when each unit retains its
execution profile and the capacity source identifies the correct shared pool.
A repository-wide idle-runner count is not a safe scheduling budget. Preserve
coverage when changing shard count or process-level parallelism.

### 3.3 Reporting-Service Archetype

Model frontend, backend and credential-bearing infrastructure as separate lanes.
Omitting irrelevant infrastructure work may reduce credential-bearing execution,
but it must never broaden the remaining jobs' authority.

Require:

- Stable logical obligations mapped to native workflows.
- Conservative coarse selection.
- Credential-profile preservation.
- Embedded same-run shadow observation.
- Fallback to the unchanged native Full Check.

## 4. Shared Provider Constraints

Actual required checks, review rules, workflow restrictions and merge semantics
must be read from the separately admitted target. No former private organization
rules are inherited by the public source or its synthetic fixtures.

```text
DeveloperAdoption does not imply ProviderWiringAuthority
```

Local adapters and policy proposals can be prepared by repository developers.
Workflow installation, required-check changes, credentials, App installation
and enforcement require the corresponding administrator's authority.
The degraded state is local proof only, never provider readiness.

## 5. Reusable Evidence From Existing CI

Only independently validated practices that preserve a named invariant are
candidates. The table states obligations, not observations that pilots passed.

| Practice | Required evidence | Coordinator disposition |
| --- | --- | --- |
| Stable aggregate required check | Exact gate identity and complete dependencies | Dynamic work must not create unstable required names. |
| Reusable workflow decomposition | Typed execution and provider-signal contracts | Do not copy consumer-specific setup into the coordinator. |
| Immutable references and least privilege | Bound action/workflow commits and job credentials | Mutable authority-bearing references remain drift or unknown. |
| Duration-informed sharding | Bounded telemetry by execution profile | Preserve selected coverage and capacity authority. |
| Credential-isolated infrastructure | Explicit credential profiles and negative tests | Omission cannot broaden credentials. |
| Native Full Check fallback | Independent execution and failure witnesses | A coordinator outage must not prevent native validation. |

Repository-specific shell duplication, fixed shard counts and mutable operational
assumptions are not reusable architecture.

## 6. Workflow Redesign Option

A separately authorized experiment may redesign a real target workflow only if
its complete contract is preferable to the incumbent. Prove against its frozen
native baseline:

```text
BehavioralCoverage(new) >= BehavioralCoverage(old)
and CredentialAuthority(new) <= CredentialAuthority(old)
and FallbackAvailability(new) >= FallbackAvailability(old)
and RequiredGateIdentity(new) = RequiredGateIdentity(old)
and OperationalComplexity(new) < OperationalComplexity(old)
```

Until native and provider witnesses establish those predicates, the existing
workflow remains authoritative and the redesign remains a proposal.

## 7. Pilot Exit Evidence

Each pilot must publish evidence tied to an immutable coordinator artifact and
an independently admitted target revision:

1. Workflow inventory and recognized execution profiles.
2. Generated configuration reviewed by the repository owner.
3. Embedded shadow planning in the native Full Check run.
4. Baseline and candidate observations bound to the same experiment.
5. Queue, runner and duration telemetry with explicit uncertainty.
6. Zero unsafe omissions over the declared sample window.
7. Outage and malformed-plan fallback exercises.
8. Rollback and stable-gate evidence.
9. Separate administrator approval before enforcement.

Local documents and unit tests cannot replace evidence requiring real GitHub
authority, credentials, runners or organization rules.
