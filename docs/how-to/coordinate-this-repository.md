# Coordinate This Repository

The self-consumer runs the repository's existing native validation families and
utility jobs through the same target registry and consumer controls distributed
to other repositories. Its workflow is
`.github/workflows/coordinated-checks.yml`. The independent `Full Check` and
`Pull Request Gate` retain their existing authority during qualification.

## Regenerate And Check

After changing native jobs, utility jobs, runtime pins or consumer controls, run:

```sh
backend/.venv/bin/python -m scripts.self_ci_generate --write
backend/.venv/bin/python -m scripts.self_ci_generate --check
```

The native job bodies remain owned by
`.github/workflows/python-persistence.yml`. The generator copies their current
steps, matrices, runners, permissions, timeouts and artifact relationships. It
adds the target plan dependency and selection condition, and projects the
native workflow environment into step-based jobs. Generated YAML and files
under `.ci-coordinator` must not be edited by hand.

Changed workflow or generated bytes also require review of their existing
`non_runtime` entrypoint disposition. Refresh the affected `workflow.documents`
and `generated.documents` fingerprints in the canonical runtime entrypoint
profile and its packaged mirror after generation. The native entrypoint test
recomputes their complete member sets and digests; generator parity alone does
not establish that separate classification.

The generator admits the resulting workflow topology, local reusable workflow
closure and exact control-job projections through the runtime's own contracts.
The existing target-artifact renderer then produces the execution registry,
empty native-job test manifest, conservative dependency graph and packaged
CommonJS control bundle. The generated inventory binds every source input by
SHA-256 and records the native aggregate's result and output predicates.

The complete Python collection, eleven native shards and coverage join form one
obligation with three witnesses. The trusted requester negative contract groups
its invocation with a separate assertion that its result is `plan_url_invalid`.
Neither helper is a standalone substitute for its complete validation family.
Manual deep API and serial qualification remain separate scopes in Full Check.
The release artifact and automatic mutation discovery workflows retain their
separate owners.

## Execute Qualification

The generated workflow has two entrypoints:

- `workflow_dispatch` executes the complete fallback without requesting a
  selected plan. It preserves the native `proof_scope` choice (`full` by
  default, or `range`) and `proofkit_base_sha` string input. For `range`, provide
  the lowercase ancestor commit SHA required by the native proof commands.
  These inputs control proof-range checks; API deep and serial qualification
  remain available only through the independent Full Check.
- A push to `ci-qualification/**` uses the real invocation classifier and
  trusted plan requester. Ordinary pull requests and branch pushes do not
  start a duplicate coordinated workflow.

Native step conditions remain unchanged. In particular, GitHub's dependency
review action runs only on pull requests; the independent native PR workflow
continues to own that provider predicate. A qualification-branch push does not
claim equivalence to every event-specific PR or release check.

An unavailable endpoint, installation binding, trust root, valid plan or
production authority cannot authorize skipping native jobs. The fallback runs
every registered native execution job. Its gate requires every job to succeed;
failure, cancellation, missing results or unexpected skipped results fail.
The generated workflow uses its own concurrency group and cannot cancel the
independent Full Check.

The qualification catalog keeps every native family, Docker/provider check,
spelling check and vulnerability feed non-omittable. It admits bounded omission
only for `utility-config` and `utility-go-static` when their complete input
responsibilities are unchanged. Config responsibility covers the matrix's
YAML/JSON/TOML surfaces and INI files. Shared tool controls remain owned by the
graph's global-risk and invalidation guards. Go responsibility includes
every discovered module's whole directory tree, including embedded data, plus
Go source/module/workspace/configuration inputs. Unadmitted Go replacement
dependencies stop generation rather than claim a closed input boundary.

The configured graph contains one node for every observed regular Git path; it
does not treat a directory node as proof about future files. Unknown/new paths,
removed or renamed paths absent from the head inventory, truncated evidence and
changes to scripts, workflows, quality tooling or toolchain controls preserve
FullCI. The input inventory binds path names and Git file modes; authenticated
head/diff evidence binds changed content. Thus an ordinary change to a known
documentation file can omit the two unaffected utilities without pretending
that unrelated application dependencies have been exhaustively discovered.
No import or service dependency edges are inferred: the omission domain is the
two direct-input utility predicates, while every native family remains selected.
External vulnerability feeds
require fresh checks even when source bytes are unchanged.

## Bind The Deployment

Materialize a repository policy only with the actual installation and repository
identities for this deployment:

```sh
backend/.venv/bin/python -m scripts.self_ci_generate --policy \
  --installation-id "$INSTALLATION_ID" \
  --repository-id "$REPOSITORY_ID" \
  --default-branch master > /tmp/ci-coordinator-self-policy.json
```

The CLI admits this document through the public repository-policy compiler and
checks that compilation preserves the generated validation catalog. It does
not activate the policy. Review and register it through the normal configuration
lifecycle, using the actual repository's current default branch.

The policy's observation rule watches the existing native Full Check for pull
requests targeting that default branch. Its `dynamicCi` section independently
contains the coordinated workflow's catalog and graph. Observation rules use
exact branch membership; the qualification workflow's `ci-qualification/**`
trigger is not an observation-rule branch pattern. Changing this observation
rule does not activate or narrow the separate qualification-push planning scope.

Set `CI_COORDINATOR_INSTALLATION_ID` and `CI_COORDINATOR_PLAN_URL` repository
variables to the reviewed deployment values. The endpoint is also the OIDC
audience. Produce `.ci-coordinator/plan-trust-root.v1.json` separately with the
existing `ci-coordinator-target-artifacts render-trust-root` command and the
deployment owner's real public plan-signing key. Commit and review that public
trust configuration at the workflow authority revision. The generator creates
no private key, example trust root or synthetic installation identity.

Before selected execution, complete the
[production admission contract](../architecture/cross-cutting/production-admission.md)
and its [activation procedure](stage-and-activate-production-authority.md): bind
the exact deployment artifact, configuration epoch, target registry, workflow
source, provider governance, same-subject shadow results, outage fallback,
rollback and active generation. The repository's existing required native gate
remains in force until a separately approved governance transition. A generated
consumer, successful manual run or registered policy does not activate omission.

## Inspect Input And Property Coverage

`python -m scripts.ci_matrix check` admits the current path inventory, concrete
declared input dispositions, and the
[blueprint risk projection](../../proofkit/ci-risk-coverage.v1.json). Each risk
row links to an existing Proofkit requirement, an exact source-bound assertion,
its registered command and its native execution modes, or explicitly records
a partial, deferred, unknown or inapplicable disposition. Review the reason and
revision trigger before treating a candidate as sufficiently covered. The
89 tool classes and 25 domain properties are separate bounded inventories.

Input membership describes the predicate actually owned by the consumer: JSON
syntax does not prove domain schemas; generated parity does not prove runtime
behavior; a resource identity check does not analyze its contents. Unknown active
roots fail admission. The risk report keeps semantic completeness and observed
execution separate from structural admission. A source change invalidates its
assertion binding until that assertion is reviewed against the new bytes.

The [coverage decision](../decisions/ci-coverage-and-advisory-closure.md) explains
these boundaries, native Go input reconciliation, early path-and-mode fallback
and the separate periodic advisory lifecycle.
